
**Domain Name System (DNS)** — это иерархическая и децентрализованная система именования для компьютеров, сервисов или других ресурсов, подключенных к Интернету или частной сети. Она связывает различную информацию с доменными именами, назначенными каждому из участников.

Прежде всего, DNS переводит легко запоминаемые доменные имена (например, `google.com`) в числовые IP-адреса, необходимые для идентификации и определения местоположения компьютерных сервисов и устройств по всему миру.

## Как работает DNS?

Процесс разрешения DNS (DNS resolution) включает в себя преобразование имени хоста в понятный компьютеру IP-адрес.

1. Когда пользователь вводит доменное имя в браузере, запрос отправляется в интернет для поиска соответствующего IP-адреса.
    
2. После того как IP-адрес найден, клиент может запросить контент с этого адреса (например, веб-страницу).
    

### Типы серверов

Инфраструктура DNS состоит из четырех основных групп серверов:

#### 1. DNS Resolver (Рекурсивный резонатор)

Это «первая остановка» в DNS-запросе. Резолвер выступает посредником между клиентом и именами серверов. Получив запрос, он либо отвечает данными из кэша, либо последовательно опрашивает корневой сервер, сервер TLD и, наконец, авторитетный сервер.

#### 2. DNS Root Server (Корневой сервер)

Корневой сервер принимает запрос от резолвера и направляет его к серверу TLD (Top-Level Domain) на основе расширения домена (`.com`, `.net`, `.org` и т.д.). Существует 13 типов корневых серверов, распределенных по всему миру с помощью Anycast-маршрутизации.

#### 3. TLD Nameserver (Сервер домена верхнего уровня)

Хранит информацию о доменах с общим расширением. Управление ими осуществляет IANA (подразделение ICANN). Делятся на две группы:

- **Общие (Generic TLD):** `.com`, `.org`, `.net`, `.edu`, `.gov`.
    
- **Коды стран (Country code TLD):** `.uk`, `.us`, `.ru`, `.jp`.
    

#### 4. Authoritative DNS Server (Авторитетный DNS-сервер)

Это последняя точка в поиске. Если сервер имеет доступ к записи, он возвращает IP-адрес резолверу, который затем передает его клиенту.

## Типы записей DNS (DNS Records)

Для корректного разрешения запросов используются различные записи:

- **A Record:** содержит IP-адрес (IPv4) для домена.
    
- **AAAA Record:** содержит IPv6-адрес для домена.
    
- **CNAME Record:** (Canonical Name) перенаправляет один домен на другой (псевдоним).
    
- **MX Record:** (Mail Exchange) указывает, куда направлять электронную почту для домена.
    
- **TXT Record:** позволяет администратору хранить текстовые заметки (часто используется для верификации владения доменом).
    
- **NS Record:** (Name Server) указывает, какие серверы являются авторитетными для данного домена.
    

## TTL (Time to Live)

**TTL** — это значение, определяющее, как долго DNS-запись должна храниться в кэше до ее обновления. Оно измеряется в секундах. Чем выше TTL, тем реже обновляется запись, что снижает нагрузку, но замедляет распространение изменений.

## Reverse DNS (Обратный DNS)

Запрос доменного имени по IP-адресу. Выполняет функцию, противоположную обычному поиску. Использует **PTR-записи**. Часто применяется почтовыми серверами для проверки легитимности отправителя.

> [!EXAMPLE] Примеры решений
> 
> Route53, Cloudflare DNS, Google Cloud DNS, Azure DNS, NS1.

# Load Balancing (Балансировка нагрузки)

**Балансировка нагрузки** позволяет распределять входящий сетевой трафик между несколькими ресурсами, обеспечивая высокую доступность и надежность путем отправки запросов только на те ресурсы, которые находятся в сети.
![[Pasted image 20260228102320.png]]
## Зачем это нужно?

Современные сайты с высоким трафиком обслуживают миллионы одновременных запросов. Чтобы масштабироваться экономически эффективно, используют группы серверов. Балансировщик стоит перед ними и направляет запросы так, чтобы:
![[Pasted image 20260228102327.png]]
- Ни один сервер не был перегружен.
    
- Максимально использовались вычислительные мощности.
    
- Если сервер выходит из строя, трафик перенаправлялся на рабочие узлы.
    

## Распределение нагрузки (Workload Distribution)

1. **Host-based:** распределение на основе имени хоста.
    
2. **Path-based:** использование всего URL (пути) для маршрутизации.
    
3. **Content-based:** проверка содержимого сообщения (например, параметров запроса).
    

## Уровни работы (OSI Layers)

- **L4 (Сетевой уровень):** работает на транспортном уровне. Использует IP-адреса и порты. Очень быстрый, но не «видит» содержимое пакетов.
    
- **L7 (Прикладной уровень):** работает на уровне приложения. Может читать HTTP-заголовки, куки и контент, выполняя сложную маршрутизацию.
    

## Типы балансировщиков

- **Software (Программные):** гибкие, экономичные, легко настраиваются под конкретные нужды (например, Nginx, HAProxy).
    
- **Hardware (Аппаратные):** физические устройства, способные обрабатывать огромный трафик. Дорогие и менее гибкие в обновлении.
    
- **DNS Load Balancing:** распределение запросов на уровне DNS. Главный минус — DNS не проверяет состояние (Health) сервера и может отправить трафик на «упавший» узел.
    

## Алгоритмы маршрутизации

|**Алгоритм**|**Описание**|
|---|---|
|**Round-robin**|Циклическая передача запросов серверам по очереди.|
|**Weighted Round-robin**|Учитывает веса (мощность) серверов.|
|**Least Connections**|Запрос уходит серверу с наименьшим числом активных соединений.|
|**Least Response Time**|Комбинирует время отклика и количество соединений.|
|**Least Bandwidth**|Выбирает сервер с наименьшим текущим трафиком (Mbps).|
|**Hashing**|На основе ключа (IP клиента или URL). Обеспечивает попадание на тот же сервер.|

## Преимущества

- **Масштабируемость (Scalability):** легкое добавление/удаление ресурсов.
    
- **Избыточность (Redundancy):** предотвращение простоев.
    
- **Гибкость (Flexibility) и Эффективность (Efficiency).**
    

## Резервирование (Redundant Load Balancers)

Сам балансировщик может стать «единой точкой отказа» (Single Point of Failure). Чтобы этого избежать, используют кластеры: активный балансировщик обрабатывает трафик, а пассивный (Passive) готов подхватить работу в случае сбоя первого.

## Ключевые функции

- **Autoscaling:** запуск и остановка ресурсов в ответ на спрос.
    
- **Sticky Sessions (Липкие сессии):** привязка пользователя к конкретному серверу для сохранения состояния.
    
- **Healthchecks:** регулярная проверка серверов на работоспособность.
